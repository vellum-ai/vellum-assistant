# Internationalization

How user-facing copy gets into the web app, and the rules that keep it
translatable. For the architecture behind this (why i18next, why ICU, how
locales resolve per shell) read the module docstrings in
[`src/i18n/`](../src/i18n/). This file is the working guide.

See also [`clients/web/AGENTS.md`](../AGENTS.md) and
[`docs/CONVENTIONS.md`](./CONVENTIONS.md).

---

## The rule

**Every string a user can read comes from a catalog.** No exceptions worth
taking without a comment explaining why.

That includes the copy people forget: `aria-label`, `placeholder`, `title`,
`alt`, toast messages, empty states, and error text. Screen-reader copy is
copy: an `aria-label` left in English is a Spanish user's button with no
usable name.

## Adding a string

**1. Pick the namespace.** It matches the directory that owns the component:

| Component lives in                                                   | Namespace |
| -------------------------------------------------------------------- | --------- |
| `src/domains/<name>/`                                                | `<name>`  |
| `src/components/`, `src/hooks/`, `src/utils/`, anything cross-domain | `common`  |

This mirrors the boundary `local/no-cross-domain-imports` already enforces, so
a string never has to move because the code did not. The namespace list lives
in [`src/i18n/namespaces.ts`](../src/i18n/namespaces.ts).

The split is for source control first: one catalog edited by everyone
converting a different screen is a merge-conflict magnet, and JSON conflicts
resolve badly.

**2. Name the key `<component>.<slot>`,** camelCase, where `<component>` is the
component's own name with a lowercase first letter:

```jsonc
// locales/en/chat.json
{
  "conversationAssets": {
    "heading": "Assets",
    "label": "{count, plural, one {# asset} other {# assets}}",
  },
}
```

- Don't repeat the namespace in the key. `chat:conversationAssets.label`, never
  `chat:chat.conversationAssets.label`.
- Don't name a key for the English copy it currently holds. `saveButton.label`,
  never `clickHereToSave`, because the copy changes and the key should not.

**3. Add it to every locale.** A key missing from a translated catalog falls
back to English, which is degraded but not broken. A key present in a
translated catalog but absent from English is a test failure, because nothing
can read it.

**4. Read it with `t()`,** naming the namespace unless it is `common`:

```tsx
import { useTranslation } from "@/i18n";

const { t } = useTranslation("chat");
return <h2>{t("conversationAssets.heading")}</h2>;
```

Outside React (stores, event handlers, toasts) use the bound `t`:

```ts
import { t } from "@/i18n";

toast.error(t("chat:composer.attachmentTooLarge", { count: oversized.length }));
```

That `t` is not reactive. A component that renders its result must use
`useTranslation()`, or it keeps showing the previous language after a switch.

Import from `@/i18n`, never from `i18next` or `react-i18next` directly. Keys
are type-checked against the English catalogs, so a typo or a key read from the
wrong namespace fails `tsc`.

## Writing messages that survive translation

**Never assemble a sentence from fragments.** This is the single most common
way to make a string untranslatable, because word order is fixed by the source
and no translator can move the count or the noun:

```tsx
// Wrong. Also wrong in English at count === 1.
`${count} items selected`;
count === 1 ? "1 asset" : `${count} assets`;
```

Use ICU `plural`, and let the catalog own the grammar:

```jsonc
"label": "{count, plural, one {# asset} other {# assets}}"
```

```tsx
t("conversationAssets.label", { count: assets.length });
```

ICU resolves the plural category through `Intl.PluralRules`, so a locale with
six plural forms gets six and the call site knows nothing about it. English has
two; Polish has four; Arabic has six. Any `? :` on a count is a bug outside
English.

**Two variants of a sentence get two keys, not a `select` branch appended to
one.** Translators get a whole sentence to work with, and languages that place
a qualifier somewhere other than the end can move it.

**Inline markup goes through `<Trans>`,** not through splitting the sentence
around the element:

```tsx
<Trans i18nKey="account.terms">
  Read the <a href="/terms">terms</a> before continuing
</Trans>
```

**Apostrophes are safe.** ICU treats `'` as an escape character only when it
precedes a syntax character, so `"you're"` renders literally. `{` and `}` in
literal copy do need escaping.

**Formatting is not copy.** Dates, numbers, currency, and lists go through
`Intl`, never a hand-built string.

## Enforcement

**`local/no-untranslated-strings`** reports JSX text, `toast()` copy, and any
prop that is not structural whose value reads as copy rather than an enum.

That last part is a denylist, not an allowlist: `className`, `href`, `data-*`,
handlers, and SVG geometry are structural, and everything else is checked. A
value counts as copy when it has a space or starts with a capital, so
`label="Save changes"` and `submitLabel="Complete signup"` are caught while
`variant="primary"` and `tone="error"` stay quiet. An allowlist of prop names
could only ever cover props someone had thought of, and three converted domains
kept shipping English through bespoke props like `toggleAriaLabel`. It is enabled **only for the paths in
`i18nEnforcedPaths`** in [`eslint.config.mjs`](../eslint.config.mjs), and that
list grows as areas are converted.

To convert an area: move its copy into the right namespace, read it with `t()`,
add the glob, and run `bun run lint` until it is quiet.

- Never add a path that still has violations in it.
- Never widen a glob to make an error go away.

**A clean lint run is not proof a domain is fully translated.** The rule reads
JSX, so copy that reaches the screen from somewhere else is invisible to it:
string literals in `.ts` data modules (channel metadata, option lists, enum
labels), messages passed to `setError()` or returned by a helper, and arrays of
literals. Adding a glob records that the JSX is converted, nothing more. When
you convert a domain, read its non-JSX modules too.

The list is the record of how far the cutover has reached. Scoping it this way
is deliberate: switched on repo-wide it would report thousands of pre-existing
literals at once, and a rule that noisy gets disabled rather than obeyed.

**The escape hatch,** for copy that genuinely must not be translated: brand
names, code identifiers, protocol tokens. Always with a reason:

```tsx
// eslint-disable-next-line local/no-untranslated-strings -- brand name
<span>Vellum</span>
```

**`catalogs.test.ts`** guards the catalogs themselves: every message parses as
ICU, no translated catalog carries a key English lacks, no placeholder is
dropped in translation, and no key sits unreferenced by any call site. That
last one matters during a fast cutover, because a deleted component leaves orphaned
copy behind, and orphans get sent to a translator and paid for.

## Testing your change

i18next is initialized for you in `test-setup.ts` and `.storybook/preview.tsx`,
both pinned to English, so component tests and stories keep asserting against
the source copy. All three entry points build their options from
[`src/i18n/config.ts`](../src/i18n/config.ts) so they cannot drift.

To see another locale in the running app, there is no picker yet. Set the
device preference from the devtools console and reload:

```js
localStorage.setItem("device:locale", "es");
location.reload();
```

That override is consulted _before_ the host, so it also masks host detection.
To test that the OS or browser language is picked up, clear it first:

```js
localStorage.removeItem("device:locale");
location.reload();
```

`document.documentElement.lang` reflects the active locale, which is the
quickest check that resolution ran at all.
